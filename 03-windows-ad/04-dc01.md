# DC01: la VM del controlador de dominio

**Paso 4 del plan** · VM creada el 28/10/2026 · Revisada el 18/11/2026

---

## Qué problema resuelve

El dominio necesita un servidor que sea controlador de dominio y DNS del lab. Es la pieza central
del Bloque 3 y de todo el trabajo de detección: los eventos de autenticación del dominio nacen acá.

## Cómo lo abordé

| Propiedad | Valor |
|---|---|
| Sistema | Windows Server 2025 Standard (evaluación de 180 días) |
| VM | Generación 2 · Secure Boot con la plantilla *Microsoft Windows* · 4 GB de RAM dinámica |
| Red | `LAB-SERVIDORES` · IP fija `10.10.10.10/24` · gateway `10.10.10.1` (`FW01`) |
| Roles | AD DS y DNS |
| Administración | SSH solo con clave, accesible únicamente desde `FW01` (ver abajo) |

### Administración remota

Para administrarlo desde la Mac, igual que los servidores Linux, instalé OpenSSH Server:

- **Firewall de Windows:** una sola regla que permite el puerto 22 **solo desde `10.10.10.1`**
  (`FW01`). Las conexiones por Tailscale llegan con ese origen. Cualquier otro equipo, incluso del
  mismo segmento, queda bloqueado.
- **`sshd_config`:** `PasswordAuthentication no` y `KbdInteractiveAuthentication no`. En Windows
  no alcanza con la primera: *keyboard-interactive* es otra forma de pedir la misma contraseña.

## Cómo lo verifiqué

| Prueba | Resultado |
|---|---|
| SSH con clave desde la Mac | ✅ |
| SSH desde `SRV01`, en el mismo segmento | ✅ Bloqueado por el firewall de Windows |
| Métodos que ofrece a un usuario sin clave | `publickey` |

## Qué aprendí

- En Windows, OpenSSH puede quedar instalado y corriendo **sin** regla en el firewall. El puerto
  aparecía cerrado aunque el servicio estaba en marcha.
- Para cerrar la contraseña en el SSH de Windows hay que apagar dos métodos, no uno.
