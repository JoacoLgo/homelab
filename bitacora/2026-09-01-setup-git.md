## Parte 1 — Git en la Mac

```bash
git --version
```
Confirma que Git está instalado. En macOS viene con las Command Line Tools de Xcode; si no está, el
propio comando ofrece instalarlas.

```bash
git config --global user.name "Joaquin Lagoria"
git config --global user.email "JoacoLgo@users.noreply.github.com"
git config --global init.defaultBranch main
```
`--global` escribe en `~/.gitconfig` y aplica a todos los repositorios de esta computadora (sin
`--global` aplicaría solo al repositorio actual, en `.git/config`).

Ese nombre y ese mail quedan **grabados dentro de cada commit, para siempre y en público**. Por eso
se usa el mail `@users.noreply.github.com` que GitHub provee: GitHub igual atribuye los commits a la
cuenta, pero el mail personal no queda expuesto a cualquiera que clone el repositorio. Está en
*GitHub → Settings → Emails → Keep my email addresses private*.

```bash
git config --list --global      # ver la configuración
git config --global --edit      # editarla a mano
```

## Parte 2 — Autenticación con GitHub por clave SSH

GitHub ya no acepta contraseña para operar por HTTPS. Las dos opciones son un token personal o una
clave SSH. La clave SSH es mejor: no expira sola, no se copia y pega, y es el mismo mecanismo que se
usa para entrar a cualquier servidor Linux — o sea que aprenderlo sirve para el resto del plan.

**La idea:** se generan dos archivos que son un par matemático. La **privada** (`id_ed25519`) no sale
nunca de la máquina. La **pública** (`id_ed25519.pub`) se le entrega a GitHub. GitHub manda un
desafío que solo la privada puede responder, y así verifica quién sos sin que la contraseña viaje.

### Si hay que hacerlo de cero

```bash
ssh-keygen -t ed25519 -C "macbook-joaquin"
```
Genera el par. `-t ed25519` elige el algoritmo (moderno, corto y rápido; RSA quedó viejo). `-C` es
solo un comentario para identificar de qué máquina es la clave cuando tengas varias cargadas en
GitHub. Pide una ruta (Enter acepta `~/.ssh/id_ed25519`) y una passphrase, que conviene poner: si te
roban el archivo, sin la passphrase no sirve.

```bash
eval "$(ssh-agent -s)"
ssh-add --apple-use-keychain ~/.ssh/id_ed25519
```
El **ssh-agent** es un programa que mantiene la clave descifrada en memoria para no escribir la
passphrase en cada operación. `--apple-use-keychain` guarda la passphrase en el Llavero de macOS
para que sobreviva al reinicio.

```bash
cat >> ~/.ssh/config <<'FIN'
Host github.com
  AddKeysToAgent yes
  UseKeychain yes
  IdentityFile ~/.ssh/id_ed25519
FIN
```
`~/.ssh/config` le dice a SSH qué clave usar para cada destino. Sin esto, teniendo varias claves,
SSH las prueba en orden y GitHub puede rechazar la conexión antes de llegar a la correcta.

```bash
pbcopy < ~/.ssh/id_ed25519.pub     # copia la clave PÚBLICA al portapapeles
```

**Dónde se pega en GitHub** (este paso es manual, no se puede automatizar):

1. Entrar a `github.com` con la cuenta.
2. Foto de perfil, arriba a la derecha → **Settings**.
3. En la columna izquierda → **SSH and GPG keys**. Link directo: `github.com/settings/keys`.
4. Botón verde **New SSH key**.
5. **Title:** un nombre que identifique la máquina, por ejemplo `MacBook Air Joaquín`.
6. **Key type:** `Authentication Key`.
7. **Key:** pegar el contenido de `id_ed25519.pub`. Empieza con `ssh-ed25519 AAAA...`.
8. **Add SSH key** y confirmar con la contraseña de GitHub.

> ⚠️ Se pega **`.pub`** y nada más. Si el texto que pegaste empieza con
> `-----BEGIN OPENSSH PRIVATE KEY-----`, esa es la privada: cancelá, no la subas a ningún lado y
> generá un par nuevo.

### Verificación

```bash
ssh -T git@github.com
```
`-T` significa "no me des una terminal, solo autenticá". La respuesta esperada:

```
Hi JoacoLgo! You've successfully authenticated, but GitHub does not provide shell access.
```

Esa segunda mitad **no es un error**: GitHub no da shell a nadie. Si dice `Permission denied
(publickey)`, la clave no está cargada en GitHub o SSH está usando otra.

```bash
ssh-add -l                          # qué claves tiene el agente cargadas
ssh -vT git@github.com              # modo verboso: muestra qué clave intenta y por qué falla
ssh-keygen -lf ~/.ssh/id_ed25519.pub   # huella de la clave, para comparar con la que figura en GitHub
```

## Parte 3 — El repositorio local

```bash
git clone git@github.com:JoacoLgo/homelab.git ~/Documents/homelab
```
Clonar por **SSH** (`git@github.com:`) y no por HTTPS (`https://github.com/`): con HTTPS te va a
pedir credenciales en cada push. Si un repositorio ya está clonado por HTTPS, se cambia el remoto sin
volver a clonar:

```bash
git remote -v                                              # ver los remotos actuales
git remote set-url origin git@github.com:JoacoLgo/homelab.git
```

En este caso el clon ya existía en el Escritorio, así que en vez de clonar de nuevo se movió entero
—historial incluido— para no terminar con dos copias:

```bash
mv ~/Desktop/homelab ~/Documents/homelab
```

Un repositorio Git es autocontenido: toda la información vive en la subcarpeta `.git/`, así que
mover la carpeta no rompe nada.

## Parte 4 — Limpieza: el zip y la carpeta duplicada

Esto ya estaba resuelto en el commit `7c34e3c`, pero es el procedimiento a recordar:

```bash
git rm homelab.zip                  # borra el archivo del disco Y lo saca del control de versiones
git rm -r --cached homelab/         # lo saca del control de versiones pero lo deja en el disco
```

La diferencia importa: `--cached` es lo que se usa cuando el archivo tiene que seguir existiendo
localmente (una carpeta de configuración, un `.env`) pero no debe estar en el repositorio.

**Por qué un zip no va en un repositorio:** Git versiona texto línea por línea, y de un archivo
binario no puede calcular diferencias — guarda una copia entera en cada cambio y el repositorio se
infla para siempre. Además el contenido no es navegable ni buscable desde la web, que es todo el
sentido de publicarlo.

**Detalle honesto:** `homelab.zip` sigue existiendo dentro del historial, en el commit que lo
agregó. Borrarlo del historial requiere reescribirlo (`git filter-repo`) y cambiar todos los hashes
posteriores. Acá no se hizo porque el zip era una copia del mismo esqueleto, sin nada sensible. **Si
lo que se filtra es una contraseña o una clave, la regla es distinta:** se rota el secreto de
inmediato y recién después se piensa en limpiar el historial. Un secreto que llegó a un repositorio
público hay que darlo por quemado.

## Parte 5 — `.gitignore`

```bash
git status --short --ignored        # muestra también lo que el .gitignore está bloqueando
git check-ignore -v archivo         # dice qué regla exactamente está ignorando un archivo
```

Lo que quedó bloqueado y por qué:

| Patrón | Motivo |
|---|---|
| `*.key`, `*.pem`, `id_ed25519*`, `.env`, `*.tfvars` | Claves y secretos. Es la categoría que no admite errores. |
| `*.iso`, `*.vhdx`, `*.avhdx`, `*.vmdk` | Discos e imágenes de VM: pesan gigabytes y GitHub corta a 100 MB por archivo. |
| `*.pcap`, `*.pcapng`, `*.evtx` | Capturas y logs: suelen traer adentro datos de la red donde se tomaron. |
| `.DS_Store` | Basura de macOS que aparece en cada carpeta que abrís en Finder. |
| Los tres documentos del plan | Tienen el Product ID de la licencia del host y datos de la red del trabajo. Se quedan en la Mac. |

> **Ojo con el orden:** `.gitignore` solo afecta a archivos que Git **todavía no está siguiendo**. Si
> un archivo ya fue commiteado, agregarlo al `.gitignore` no lo saca: hay que hacer
> `git rm --cached` primero.

## Parte 7 — Commits y push

```bash
git add archivo                     # prepara un archivo para el próximo commit
git add -A                          # prepara todos los cambios, incluidos borrados
git status                          # qué está preparado y qué no. Correlo siempre antes de commitear
git diff                            # cambios que todavía NO están preparados
git diff --staged                   # cambios que SÍ están preparados: lo que va a entrar al commit
git commit -m "Mensaje"             # confirma los cambios preparados
git log --oneline                   # el historial, una línea por commit
git push                            # sube los commits al remoto
```

**Commits atómicos:** uno por tipo de cambio, no uno gigante con todo. Sirve para tres cosas
concretas: leer el historial y entender qué pasó, revertir un cambio puntual sin arrastrar el resto
(`git revert <hash>`), y encontrar en qué commit se rompió algo (`git bisect`).

**El mensaje** se escribe en presente y describe **qué cambia y por qué**, no qué archivos tocaste
—eso ya lo dice el diff. "Reescribe el README con el laboratorio real en Hyper-V" sirve;
"actualizo cosas" no le sirve a nadie, incluido vos dentro de dos meses.

## El flujo mínimo, para la próxima vez

Trabajo del día a día, una vez que todo está configurado:

```bash
cd ~/Documents/homelab
git pull                            # traer lo que haya cambiado en GitHub antes de empezar
# ...escribir, editar, crear archivos...
git status                          # ver qué cambió
git diff                            # revisar los cambios línea por línea
git add 00-diseno/01-conceptos-virtualizacion.md
git commit -m "Escribe los conceptos de virtualización del Paso 1"
git push
```

Si algo sale mal:

```bash
git restore archivo                 # descartar cambios no guardados de un archivo
git restore --staged archivo        # sacar un archivo del área de preparación (sin perder el cambio)
git commit --amend                  # corregir el mensaje del último commit (solo si NO se pusheó)
git log --oneline --stat            # ver qué archivos tocó cada commit
git show <hash>                     # ver un commit completo
```

## Qué aprendí

- **Verificar antes de ejecutar.** Media guía de internet no aplicaba porque el trabajo ya estaba
  hecho.
- **El par de claves SSH:** la pública se reparte, la privada no sale nunca de la máquina. El
  ssh-agent existe para no tipear la passphrase todo el tiempo.
- **`git rm` vs. `git rm --cached`:** el primero borra del disco, el segundo solo del control de
  versiones. Confundirlos borra archivos que querías conservar.
- **El historial de Git es permanente.** Borrar un archivo hoy no lo saca de los commits de ayer. De
  ahí que el `.gitignore` se escriba **antes** y no después.
- **Un repositorio de portfolio se escribe para alguien que no conoce el proyecto.** Si el README
  describe un laboratorio que no existe, el problema no es de documentación: es que el lector no
  puede confiar en nada de lo que lea después.
